## S0 计算机四大件基础

> 架构师的第一课：你写的每一行Java代码，最终都跑在这四层之上。不理解这四层，JUC/JVM/Netty/Redis/Kafka的理解永远是"背结论"而非"真正理解"。

### 0.1 数据结构与算法

#### 核心认知框架

```
数据结构 = 数据怎么组织（决定了你能不能高效地找到/修改它）
算法 = 你怎么操作数据（决定了操作代价有多大）
复杂度 = 代价的度量（告诉你规模增长时性能会怎么变）
```

#### 0.1.1 数组与链表

**数组**：连续内存空间，通过基地址+偏移量O(1)随机访问，插入/删除O(N)(需要移动元素)。

**链表**：非连续内存，每个节点存指针，访问O(N)(需从头遍历)，插入/删除O(1)(改指针即可)。

**架构师深层认知——Cache友好性**：
```
数组：元素连续存储 → CPU预取+Cache Line命中 → 实际遍历速度比链表快5-10倍
链表：节点分散在堆中 → 每次访问可能Cache Miss → CPU频繁等内存 → 实际遍历慢

这就是为什么：
  - ArrayList遍历比LinkedList快(即使理论上都是O(N))
  - 链表在工程中"插入快"的前提是已经定位到节点，定位本身O(N)
  - 高性能队列(Disruptor)用环形数组而非链表
```

**大厂实践**：LMAX Disruptor用环形数组(RingBuffer)+Cache Line补齐实现单线程QPS千万级，核心原因之一就是数组的Cache预取友好性。

#### 0.1.2 哈希表

**核心原理**：`index = hash(key) % capacity`，通过哈希函数把key映射到数组下标。

**Java哈希表演进**（架构师必须理解的设计演进）：

```
HashMap JDK7: 数组+链表，hash冲突用拉链法
  问题: 链表过长时查询退化为O(N)
  
HashMap JDK8: 数组+链表+红黑树
  优化: 链表长度>8且数组长度>64 → 转红黑树(O(logN))
  退化为链表: 红黑树节点<6 → 退回链表(链表在节点少时更快)
  为什么阈值8? 泊松分布下，负载因子0.75时链表长度达8的概率=0.00000006

ConcurrentHashMap JDK7: Segment[16]分段锁
  问题: 并发度固定为16，Segment扩容代价大
  
ConcurrentHashMap JDK8: CAS+synchronized(锁桶节点)
  优化: 锁粒度从Segment(16段)→单个桶节点(并发度=数组长度)
  插入: 空桶用CAS，非空用synchronized(避免大量CAS自旋)
```

**架构师生产经验**：
- HashMap初始化指定容量：`new HashMap<>(expectedSize / 0.75f + 1)`避免扩容
- ConcurrentHashMap在高并发写场景，桶锁竞争→考虑LongAdder代替AtomicInteger计数
- 哈希攻击(恶意构造哈希冲突的key)→JDK8红黑树已防御，但仍有CPU开销

#### 0.1.3 树与B+树

**B+树**是架构师必须深入理解的数据结构——MySQL/PostgreSQL/Oracle的索引都基于B+树。

**B+树为什么是数据库索引的最优解？**

```
核心约束: 磁盘IO是最大瓶颈(一次随机IO≈10ms，一次顺序IO≈0.01ms)

B+树设计:
  1. 节点大小=磁盘页(InnoDB 16KB) → 一次IO读一页 → IO次数=树高
  2. 非叶子节点只存key+指针 → 一个16KB页存~1170个指针(假设key=8B+指针=6B)
  3. 叶子节点存完整数据行 → 一个16KB页存~16行(假设行1KB)
  4. 叶子节点用双向链表串接 → 范围查询极快(顺序IO)

3层B+树存多少行? 1170 × 1170 × 16 ≈ 2190万行
4层B+树存多少行? 1170 × 1170 × 1170 × 16 ≈ 256亿行
→ 千万级数据只需2-3次磁盘IO，这就是B+树的威力
```

**vs红黑树**：红黑树是二叉树，树高=log₂(N)，千万数据树高≈24，最多24次磁盘IO→不可接受。

**vs LSM树**：写密集场景(写>>读)用LSM树(RocksDB/HBase/Cassandra)——顺序写MemTable+后台Compaction，写性能远超B+树，但读需要查多层→读性能较差。

**架构师判断**：读多写少→B+树(MySQL)；写多读少→LSM树(Cassandra/RocksDB)；内存中→红黑树/跳表。

#### 0.1.4 跳表

**核心原理**：多层有序链表，第0层是完整链表，每往上一层是下一层的"快速通道"(每2个节点保留1个)，查找从最高层开始逐步下降→O(logN)。

**Redis ZSET为什么用跳表不用红黑树？**（Redis作者antirez的解释）：
1. 实现简单：跳表~100行代码 vs 红黑树~300+行，Bug更少
2. 范围查询天然高效：沿底层链表顺序扫描 vs 红黑树需中序遍历(指针追逐→Cache不友好)
3. 并发友好：插入/删除只修改局部指针 vs 红黑树需旋转(锁粒度大)
4. 内存可控：层高随机但期望logN，额外内存≈O(N)

**架构师锚定**：Java的ConcurrentSkipListMap/ConcurrentSkipListSet是跳表的并发实现，适合高并发有序场景(如延迟队列/排行榜)。

#### 0.1.5 复杂度与算法思想

**架构师需要的不是刷1000道LeetCode，而是建立"复杂度直觉"**：

| 场景 | 复杂度 | 直觉判断 |
|------|--------|---------|
| 哈希查找 | O(1) | 快，但哈希冲突+扩容是隐患 |
| 二分查找/树查找 | O(logN) | 很快，N翻倍只多1次操作 |
| 线性扫描 | O(N) | 百万级数据≈百万次操作，1-10ms |
| 排序 | O(NlogN) | 百万级数据≈2千万次操作，100ms级 |
| 嵌套循环 | O(N²) | 万级数据≈1亿次操作，秒级→需优化 |
| 全排列/子集 | O(2^N) | N>30就不可计算→必须剪枝/DP |

**算法思想速查**：
- **分治**：大问题拆子问题(MergeSort/QuickSort/MapReduce)
- **贪心**：每步选局部最优(不一定全局最优，适用：Huffman/最短路径Dijkstra/最小生成树)
- **动态规划**：最优子结构+重叠子问题→记忆化→避免重复计算(背包/LCS/编辑距离)
- **回溯**：试错+剪枝(N皇后/全排列/组合)

### 0.2 计算机组成原理

#### 核心认知框架

```
你写的Java代码 → javac编译 → 字节码 → JIT编译 → 机器指令 → CPU执行
                                                    ↓
                                    寄存器 ← Cache ← 主存 ← 磁盘
```

#### 0.2.1 存储体系与Cache

**金字塔结构**（速度递减、容量递增、价格递减）：
```
CPU寄存器(≈0.3ns, <1KB)
  → L1 Cache(≈1ns, 32-64KB/核)
    → L2 Cache(≈4ns, 256KB-1MB/核)
      → L3 Cache(≈12ns, 4-32MB共享)
        → 主存DRAM(≈100ns, 8-128GB)
          → SSD(≈100μs, TB级)
            → HDD(≈10ms, TB级)
```

**Cache Line(64字节)**：CPU从主存加载数据的最小单位。即使你只要1个long(8字节)，也会加载包含它的整个64字节Cache Line。

**局部性原理**——为什么Cache有效：
- **时间局部性**：刚访问的数据很可能很快再访问(循环变量)
- **空间局部性**：刚访问的数据附近的数据很可能很快被访问(数组遍历)
- 这就是数组遍历比链表快的根本原因——数组连续存储，Cache Line预取有效

#### 0.2.2 伪共享(False Sharing)

**核心问题**：两个不相关的volatile变量如果在同一Cache Line中，线程A修改变量x会导致线程B的整个Cache Line失效(即使B只读变量y)。

**实战案例**：
```java
// ❌ 伪共享：x和y在同一Cache Line
class Bad {
    volatile long x;  // 8字节
    volatile long y;  // 8字节，和x在同一Cache Line
}
// 线程A写x → MESI发送Invalidate → 线程B的Cache Line失效 → 线程B读y要重新从主存加载

// ✅ Cache Line补齐：x和y不在同一Cache Line
class Good {
    volatile long x;
    long p1,p2,p3,p4,p5,p6,p7;  // 7×8=56字节填充，x独占一个Cache Line
    volatile long y;
}
```

**JDK解决方案**：`@jdk.internal.vm.annotation.Contended`注解(JDK8+)，JVM自动补齐Cache Line。需加JVM参数`-XX:-RestrictContended`。

**大厂实践**：
- **LongAdder**：Cell数组每个Cell用@Contended补齐，避免不同Cell伪共享→比AtomicLong高并发快5-10倍
- **Disruptor**：RingBuffer的cursor和各Consumer的sequence用Cache Line补齐→单线程QPS千万级

#### 0.2.3 MESI协议与内存屏障

**MESI四种状态**：
```
Modified:  该Cache Line的数据已被修改，与主存不一致，只有本核有副本
Exclusive: 该Cache Line的数据与主存一致，只有本核有副本
Shared:    该Cache Line的数据与主存一致，多个核都有副本
Invalid:   该Cache Line无效，需要从主存重新加载
```

**MESI → Java内存模型(JMM)的映射链**：
```
MESI协议(硬件层)
  → 内存屏障(CPU指令: sfence/mfence/lfence)
    → JMM(Java内存模型: happens-before/as-if-serial)
      → volatile/synchronized/final的语义
```

**内存屏障四种**：

| 屏障 | 作用 | 对应Java |
|------|------|---------|
| LoadLoad | Load1; LoadLoad; Load2 → 保证Load1在Load2之前读 | volatile读之后 |
| StoreStore | Store1; StoreStore; Store2 → 保证Store1在Store2之前写 | volatile写之前 |
| LoadStore | Load1; LoadStore; Store2 → 保证Load1在Store2之前读 | volatile读之后 |
| StoreLoad | Store1; StoreLoad; Load2 → 保证Store1对Load2可见 | volatile写之后(代价最高) |

**架构师关键**：volatile写插入StoreLoad屏障(代价最高→完整内存屏障)，volatile读插入LoadLoad+LoadStore(轻量)。这就是volatile写比读慢的原因。

#### 0.2.4 流水线与分支预测

**CPU流水线**：把指令执行分成取指(IF)→译码(ID)→执行(EX)→访存(MEM)→写回(WB)五级，各级并行工作→IPC(每周期指令数)接近1。

**分支预测失败代价**：预测失败→流水线排空(Bubble)→浪费15-20个CPU周期→性能下降。

**架构师实践**：
- 数据有序化：对有序数据分支预测准确率接近100%
- 用位运算替代if-else：`(a > b) ? a : b` → `b + ((a - b) & ((a - b) >> 31))`
- JIT的Profile-Guided Optimization：JIT统计分支频率→优化热点路径

### 0.3 操作系统核心

#### 核心认知框架

```
你的Java程序运行在用户态
  → 需要IO/锁/网络时，系统调用陷入内核态
    → 内核操作硬件
      → 返回用户态
```

#### 0.3.1 进程与线程

**1:1模型(Java线程=OS线程)**：
```
Java new Thread() → OS pthread_create() → 分配1MB栈空间+内核线程对象
线程启动 → OS调度器分配CPU时间片 → 执行 → 时间片用完/阻塞 → 上下文切换
```

**上下文切换代价**：
```
保存: 寄存器(16+个) + 程序计数器 + 栈指针 + FPU状态 ≈ 几百字节
切换: 用户态→内核态 + 保存旧线程 + 加载新线程 + TLB刷新(如果跨进程)
总代价: ≈ 1-10μs
```

**架构师排查**：
```bash
vmstat 1          # cs列=每秒上下文切换次数, >10万需关注
pidstat -w -p PID 1  # cswch=自愿切换(IO等待), nvcswch=非自愿切换(时间片用完)
```

**为什么线程池参数难调？** 因为取决于任务类型：
- CPU密集：线程数=CPU核数+1(+1是留余量给偶发缺页)
- IO密集：线程数=CPU核数×2 或 =CPU核数×(1+等待时间/计算时间)
- 混合型：拆分CPU池和IO池，或用弹性线程池

#### 0.3.2 用户态与内核态

**系统调用流程**：
```
用户程序调用read()
  → libc包装 → 触发syscall指令(int 0x80/sysenter/syscall)
    → CPU切换到内核态(CS:RIP→内核入口)
      → 内核执行do_sys_read()
        → 数据从磁盘→内核缓冲区(Page Cache)
          → 拷贝到用户缓冲区
            → 返回用户态
```

**架构师关键认知**：Java中的每一次synchronized重量级锁、每一次Blocking IO、每一次文件读写都涉及用户态↔内核态切换。**高性能的本质就是减少这种切换**。

```
synchronized锁升级:  偏向锁(无系统调用) → 轻量锁(CAS,无系统调用) → 重量级锁(mutex,有系统调用)
epoll vs select:     epoll内核维护就绪列表,减少系统调用次数
零拷贝:             sendfile()在内核态完成,用户态零参与
```

#### 0.3.3 epoll详解

**三种IO多路复用对比**：

```
select:
  - 最多监听1024个fd(FD_SETSIZE宏)
  - 每次调用需要把fd_set从用户态拷贝到内核态(O(N)拷贝)
  - 返回后需要遍历所有fd找就绪的(O(N)遍历)
  - 触发模式: 仅水平触发(LT)

poll:
  - 无fd数量限制(用pollfd数组)
  - 仍需O(N)拷贝+O(N)遍历
  - 触发模式: 仅水平触发(LT)

epoll:
  - 无fd数量限制
  - epoll_create: 内核创建eventpoll对象(红黑树+就绪链表)
  - epoll_ctl: 添加/修改/删除fd,只操作红黑树(O(logN)),不需全量拷贝
  - epoll_wait: 只返回就绪链表中的fd, O(1)就绪检测
  - 触发模式: LT(水平触发) + ET(边缘触发)
```

**LT vs ET**：
```
LT(水平触发): 只要fd有数据可读,epoll_wait每次都返回 → 编程简单,可能重复通知
ET(边缘触发): fd从无数据→有数据时只通知一次 → 编程复杂(必须一次读完),效率更高

Netty用ET模式 → 需要循环读直到EAGAIN
Redis用LT模式 → 编程简单,单线程处理也足够快
```

#### 0.3.4 零拷贝

**传统read+write(4次拷贝+4次上下文切换)**：
```
1. DMA: 磁盘 → 内核Page Cache          (DMA拷贝,不经过CPU)
2. CPU: 内核Page Cache → 用户Buffer      (CPU拷贝,read())
3. CPU: 用户Buffer → Socket Buffer       (CPU拷贝,write())
4. DMA: Socket Buffer → 网卡             (DMA拷贝,不经过CPU)
```

**mmap(3次拷贝)**：文件映射到用户空间，省略第2次拷贝(用户Buffer)。
```
mmap() → 文件映射到用户虚拟地址空间 → 用户直接读写映射区域 → 省1次CPU拷贝
RocketMQ CommitLog用mmap → 写消息直接写映射区域
```

**sendfile(2次拷贝)**：内核直接从文件fd→Socket fd，用户程序零参与。
```
sendfile() → DMA:磁盘→内核Buffer → DMA:内核Buffer→网卡 → 用户态零参与
Kafka消息发送用sendfile → Consumer从文件直发网络,零用户态拷贝
```

**架构师认知**：Kafka吞吐高于RocketMQ的原因之一：Kafka用sendfile(2次拷贝)，RocketMQ用mmap(3次拷贝)。但RocketMQ选mmap是因为需要更灵活的消息过滤和事务消息支持。

#### 0.3.5 Cgroup与Namespace

**Namespace 6种隔离(≈"你只能看到这些")**：
```bash
# 查看当前进程的Namespace
ls -la /proc/self/ns/
```

| Namespace | 隔离内容 | 系统调用 | Docker参数 |
|-----------|---------|---------|-----------|
| PID | 进程ID(容器内PID 1≠宿主PID) | clone(CLONE_NEWPID) | --pid |
| NET | 网络栈(独立IP/端口/路由表) | clone(CLONE_NEWNET) | --network |
| MNT | 文件系统挂载点 | clone(CLONE_NEWNS) | --mount |
| USER | 用户/用户组UID/GID | clone(CLONE_NEWUSER) | --user |
| IPC | 信号量/消息队列/共享内存 | clone(CLONE_NEWIPC) | --ipc |
| UTS | 主机名hostname | clone(CLONE_NEWUTS) | --uts |

**Cgroup资源限制(≈"你只能用这些")**：
```bash
# CPU限制: 容器最多用1.5个CPU核
docker run --cpus=1.5 ...
# 内存限制: 容器最多用2GB内存
docker run --memory=2g ...
# IO限制: 容器最多读20MB/s,写10MB/s
docker run --device-read-bps /dev/sda:20mb --device-write-bps /dev/sda:10mb ...
```

**架构师锚定**：`docker run = 创建Namespace(隔离) + 创建Cgroup(限制) + UnionFS(分层镜像)`。K8s Pod = 共享NET/MNT/IPC Namespace的容器组 + 各自Cgroup资源限制。

### 0.4 计算机网络核心

#### 核心认知框架

```
应用层: HTTP/DNS/gRPC    ← 你写的代码在这层
传输层: TCP/UDP           ← 端口+可靠传输/不可靠传输
网络层: IP/ICMP/ARP       ← 寻址+路由
链路层: Ethernet/WiFi     ← MAC地址+帧传输
物理层: 光缆/双绞线/无线电  ← 比特流
```

#### 0.4.1 TCP核心机制

**三次握手**：
```
Client                              Server
  |-- SYN(seq=x) ------------------>|   (1) Client: "我想连接"
  |<-- SYN+ACK(seq=y,ack=x+1) ------|   (2) Server: "收到,我也想连接"
  |-- ACK(ack=y+1) ----------------->|   (3) Client: "确认,双方都能收发"
```
**为什么不能两次？** 两次握手→Server发出SYN+ACK就认为连接建立→但Client可能没收到→Server浪费资源(历史SYN问题)。

**四次挥手**：
```
Client                              Server
  |-- FIN ------------------------->|   (1) Client: "我没数据要发了"
  |<-- ACK -------------------------|   (2) Server: "收到,但我可能还有数据"
  |   (Server继续发送剩余数据)          (3) 半关闭状态
  |<-- FIN -------------------------|   (4) Server: "我也没数据了"
  |-- ACK ------------------------->|   (5) Client: "确认"
  |   (Client等2MSL后关闭)              (6) TIME_WAIT状态(2MSL≈60s)
```

**TIME_WAIT问题**：
- Client高并发短连接→大量TIME_WAIT(每个占1个本地端口)→端口耗尽(65535个)
- **解决方案**：
  1. 长连接池(HTTP Keep-Alive/数据库连接池)——根本解决方案
  2. `tcp_tw_reuse=1`(允许复用TIME_WAIT端口,需tcp_timestamps=1)
  3. `tcp_max_tw_buckets`调小(超过直接RST释放)
  4. **不要设tcp_tw_recycle=1**(NAT环境下会导致其他Client连接失败)

#### 0.4.2 TCP拥塞控制

**Reno/Cubic(基于丢包)**：
```
慢启动: cwnd=1 → 每个RTT翻倍(1→2→4→8→16...) → 到达ssthresh转拥塞避免
拥塞避免: cwnd每个RTT+1(线性增长) → 直到丢包
快速重传: 收到3个重复ACK → 立即重传(不等超时)
快速恢复: ssthresh=cwnd/2, cwnd=ssthresh → 进入拥塞避免
```

**BBR(基于带宽+RTT, Google 2016)**：
```
核心思想: 不依赖丢包判断拥塞,而是测量最大带宽(BtlBw)和最小RTT(RTprop)
  → 发送速率=max带宽, 发送量=BDP(带宽×延迟)

优势: 
  - 在有1%丢包的网络中, Cubic吞吐下降90%, BBR几乎不变
  - 在长肥网络(高带宽高延迟)中, BBR比Cubic吞吐高2-100倍
  - Google已在YouTube/Google全球部署BBR

启用: sysctl -w net.ipv4.tcp_congestion_control=bbr (需Linux 4.9+)
```

#### 0.4.3 TLS握手

**ECDHE握手(TLS 1.2, 2-RTT)**：
```
1. ClientHello: 支持的加密套件+随机数+支持的TLS版本
2. ServerHello: 选定套件+随机数+证书+ServerKeyExchange(ECDHE参数)
3. ClientKeyExchange: ECDHE公钥 → 双方计算出预主密钥
4. 双方用(随机数1+随机数2+预主密钥)生成会话密钥
5. 后续通信用AES-GCM对称加密
```

**TLS 1.3(1-RTT)**：
```
1. ClientHello: 直接发送KeyShare(ECDHE公钥) → 省1个RTT
2. ServerHello: 选定套件+KeyShare+证书 → 双方已有会话密钥
3. 0-RTT: 如果有之前的PSK, Client可以在第一个包就发应用数据
```

**架构师优化**：
- Session Ticket: 服务端加密Session信息发给客户端→下次握手1-RTT
- OCSP Stapling: 服务端附带证书吊销状态→客户端不用再查CA
- 硬件加速: AES-NI指令集→对称加密性能提升10倍+

#### 0.4.4 网络设备与转发

**同网段通信**：主机A→查ARP表→找到目标MAC→交换机转发(MAC表)
**跨网段通信**：主机A→ARP找默认网关MAC→发给路由器→路由器查路由表→转发到下一跳

**架构师锚定**：
- Docker Bridge网络 = 虚拟交换机(docker0) + NAT(iptables)
- K8s Calico = BGP路由 + 虚拟路由器(每个Node是一个"路由器")
- K8s Flannel = VXLAN overlay网络(在三层网络之上构建二层虚拟网络)

## S1 网络编程与Netty

> 架构师视角：Netty是中间件世界的"普通话"。Dubbo/Nacos/RocketMQ/Elasticsearch/Flink的通信层都基于Netty。理解Netty = 拿到阅读中间件源码的钥匙。

### 1.1 BIO → NIO → AIO 演进

```
BIO(Blocking IO):
  一个连接一个线程 → 连接数=线程数 → 千级连接耗千个线程 → 1MB栈/线程 → 内存爆炸
  典型: Tomcat默认模式(maxConnections=8192但线程池默认200)

NIO(Non-blocking IO):
  一个线程用Selector管理多个连接 → 连接数>>线程数 → 万级连接少量线程
  核心: Channel(双向通道) + Buffer(数据容器) + Selector(多路复用器)
  典型: Netty/Tomcat NIO模式

AIO(Asynchronous IO):
  操作系统完成IO后回调通知 → Windows IOCP成熟, Linux AIO不成熟
  Linux下Netty仍用NIO+epoll(因为Linux AIO性能不如epoll)
```

### 1.2 Reactor模式三种变体

```
单Reactor单线程:
  一个线程: accept + IO读写 + 业务处理
  适用: 轻量级(QPS<1万), 如Redis
  
单Reactor多线程:
  一个线程: accept
  线程池: IO读写 + 业务处理
  适用: 中等并发, 但Reactor线程仍是瓶颈

主从Reactor多线程(Netty模型):
  bossGroup(N个线程): accept新连接
  workerGroup(M个线程): IO读写
  业务线程池(可选): 业务处理(耗时操作不阻塞IO线程)
  适用: 高并发(QPS>10万)
```

### 1.3 Netty核心组件

```
EventLoop: 一个线程 + 一个Selector + 一个TaskQueue
  → 不断循环: select() → processSelectedKeys() → runAllTasks()
  
Channel: 一个网络连接的抽象, 绑定一个EventLoop
  → NioSocketChannel(TCP) / NioServerSocketChannel(服务端)
  
ChannelPipeline: ChannelHandler链, 双向链表
  → 入站(head→tail): 读数据→解码→业务处理
  → 出站(tail→head): 编码→写数据
  
ByteBuf: 字节容器, 比JDK ByteBuffer好用
  → 池化+堆外内存+零拷贝
  → 引用计数(ReferenceCounted): release()释放, 泄漏检测
```

### 1.4 粘包/拆包与解决方案

**根本原因**：TCP是字节流协议，没有消息边界。Nagle算法可能把多个小包合并发送(粘包)，MTU限制可能把大包分片传输(拆包)。

**四种解决方案**：

| 方案 | 原理 | 优缺点 | Netty实现 |
|------|------|--------|-----------|
| 固定长度 | 每条消息固定N字节 | 简单但浪费带宽 | FixedLengthFrameDecoder |
| 分隔符 | 用\n或\r\n分隔 | 简单但消息内容不能含分隔符 | DelimiterBasedFrameDecoder |
| 长度字段 | 消息头含长度(最常用) | 灵活高效,工业标准 | LengthFieldBasedFrameDecoder |
| TLV | Type+Length+Value | 协议标准,最规范 | 自定义Decoder |

**架构师实战**：Dubbo协议=Magic Number(2B)+Flag(1B)+Status(1B)+RequestID(8B)+DataLength(4B)+Body→长度字段方案。

### 1.5 手写RPC框架(架构师理解Netty的最佳方式)

```
一个RPC调用流程:
1. Client代理 → 序列化请求 → 通过Netty Channel发送 → 等待响应
2. Server接收 → 解码 → 找到实现类 → 反射调用 → 序列化响应 → 写回Channel
3. Client收到响应 → 反序列化 → 返回结果

关键设计:
- 服务注册: 接口名 → 实现类实例(Map<serviceName, Object>)
- 动态代理: JDK Proxy生成Client代理对象
- 序列化: Hessian/Kryo/Protostuff(比JDK序列化快10倍+)
- 网络传输: Netty + LengthFieldBasedFrameDecoder(解决粘拆包)
- 异步转同步: CompletableFuture / DefaultPromise
```

**架构师建议**：手写一个简化版RPC框架(300行代码)比看100篇Netty博客都有效。理解了这个流程，Dubbo/gRPC的架构你就懂了80%。

## S2 JUC与JVM源码深挖

> 架构师视角：JUC和JVM你已经会用了，这个阶段是从"会用"到"读懂源码+能定位生产问题"的跃迁。

### 2.1 AQS源码精读

**AQS(AbstractQueuedSynchronizer)**是JUC锁体系的基石——ReentrantLock/CountDownLatch/Semaphore/ReentrantReadWriteLock都基于AQS。

**核心设计**：
```
state: 同步状态(0=未锁,1=已锁,>1=重入)
exclusiveOwnerThread: 独占模式下的持有线程
CLH队列: 双向链表, 头节点(dummy)→等待节点→...→尾节点
  每个Node: waitStatus(SIGNAL/CANCELLED/CONDITION/PROPAGATE)
            + thread(等待线程)
            + prev/next(前后节点)
```

**ReentrantLock.lock()流程**：
```
1. tryAcquire(1): CAS(state, 0, 1)
   成功 → 设置exclusiveOwnerThread=当前线程 → 获取锁
   失败 → 当前线程已是持有者 → state++(可重入) → 获取锁
   
2. addWaiter(EXCLUSIVE): 当前线程封装为Node → CAS入CLH队列尾部

3. acquireQueued(node, 1): 自旋
   如果前驱是head → tryAcquire(1) → 成功则出队
   否则 → shouldParkAfterFailedAcquire() → 设置前驱waitStatus=SIGNAL
        → parkAndCheckInterrupt() → LockSupport.park(this) → 线程挂起
```

**ReentrantLock.unlock()流程**：
```
1. tryRelease(1): state-- → 如果state=0 → 设置exclusiveOwnerThread=null → return true

2. unparkSuccessor(head): 找到head后第一个未取消的Node → LockSupport.unpark(node.thread) → 唤醒等待线程
```

**架构师源码阅读路线**：
```
ReentrantLock(入门,独占模式) 
  → CountDownLatch(共享模式,多个线程同时唤醒)
    → CyclicBarrier(理解generation和break语义)
      → Semaphore(理解共享模式acquire/release)
        → ReentrantReadWriteLock(理解读锁共享+写锁独占)
```

### 2.2 ConcurrentHashMap JDK8源码

**put()核心流程**：
```
1. 计算hash: (h ^ (h >>> 16)) & HASH_BITS → 扰动+保证正数

2. 空桶: tab[i] == null → CAS写入新Node → 成功则return
   (注意: 空桶用CAS不用synchronized → 减少锁竞争)

3. 非空桶: synchronized(tab[i]) → 锁住桶头节点
   3a. 链表: 遍历查找key → 找到则更新value → 没找到则尾插新Node
   3b. 红黑树: TreeNode.find() → 找到则更新 → 没找到则TreeNode.putTreeVal()
   3c. 链表长度≥8 → treeifyBin() → 数组长度<64先扩容,≥64才转红黑树

4. addCount(): 计数+检查是否需要扩容
   → CounterCell[]数组(类似LongAdder,避免CAS竞争)
   → 扩容: transfer(),支持多线程协助扩容
```

**架构师关键设计**：
- **锁粒度**：JDK7锁Segment(16段)，JDK8锁桶节点(并发度=数组长度)
- **空桶CAS + 非空桶synchronized**：CAS适合低竞争(空桶概率高)，synchronized适合高竞争(有节点说明竞争激烈)
- **多线程协助扩容**：每个线程负责迁移一段桶(transferIndex递减分配)，加快扩容速度

### 2.3 线程池源码与生产调优

**ThreadPoolExecutor核心参数**：
```
corePoolSize:   核心线程数(即使空闲也不销毁,除非allowCoreThreadTimeOut)
maximumPoolSize: 最大线程数(核心+临时)
keepAliveTime:  临时线程空闲存活时间
workQueue:       任务队列(选择策略是架构师的核心决策)
threadFactory:   线程工厂(自定义线程名→方便排查)
handler:         拒绝策略(队列满+线程满时的处理)
```

**任务提交流程**：
```
提交任务 → 当前线程数 < corePoolSize → 创建核心线程执行
        → 当前线程数 ≥ corePoolSize → 任务入workQueue
          → 队列满 && 线程数 < maximumPoolSize → 创建临时线程执行
            → 队列满 && 线程数 = maximumPoolSize → 拒绝策略
```

**四大拒绝策略**：
```
AbortPolicy(默认): 抛RejectedExecutionException → 调用方感知
CallerRunsPolicy: 调用方线程执行任务 → 降速但不丢弃
DiscardPolicy:    静默丢弃 → 适合日志等可丢失任务
DiscardOldestPolicy: 丢弃队列头部最旧任务+重新提交 → 适合实时性要求
```

**架构师生产经验**：
- **线程池大小**：CPU密集=核数+1，IO密集=核数×2或用公式`N×(1+W/C)`
- **队列选择**：有界队列(ArrayBlockingQueue/LinkedBlockingQueue指定容量)→防止OOM；无界队列是生产隐患
- **线程命名**：`new ThreadFactory() { prefix = "order-process-pool-" + counter++ }`→jstack能定位问题
- **优雅关闭**：`shutdown()`→等待任务完成→`awaitTermination(timeout)`→`shutdownNow()`→处理未完成任务
- **美团经验**：线程池参数动态调参(接入配置中心)，运行时修改core/max/queueSize无需重启

### 2.4 JVM调优实战

**GC算法演进**：
```
Serial:     单线程GC, STW长, 适合客户端/小堆(<100MB)
ParNew:     Serial多线程版, 配合CMS使用
CMS:        并发标记清除, 初始标记(STW)→并发标记→重新标记(STW)→并发清除
            问题: CPU敏感+浮动垃圾+Concurrent Mode Failure+内存碎片
G1:         分Region, 并发标记+混合收集, 可控停顿(-XX:MaxGCPauseMillis)
            JDK9默认, 适合6GB+堆
ZGC:        几乎全并发, STW<10ms(不随堆增大而增加), 适合大堆(100GB+)和低延迟
            JDK15生产可用, JDK21分代ZGC更优
Shenandoah: 类似ZGC, RedHat开发, JDK12+可用
```

**美团ZGC实战(2025)**：
```
场景: 美团3000+Java应用从JDK8+CMS/G1迁移到JDK17+ZGC
结果: TP9999下降220-380ms(18%-74%), 机器成本降低10%

关键经验:
1. ZGC适合高QPS(>1万)应用, 低QPS应用G1够用
2. 迁移JDK8→17最大障碍: 模块化(JPMS)限制反射→需大量--add-opens参数
3. GC优化是最后的手段, 架构和代码优化优先
4. ZGC参数简单: -XX:+UseZGC -Xmx = 几乎不用调
```

## S3 Spring全家桶源码深挖

> 架构师视角：你每天都在用Spring，但出了问题你能看懂源码定位吗？Bean创建失败/事务失效/循环依赖/自动装配不生效——这些生产常见问题都需要源码级理解。

### 3.1 IoC容器启动流程

**ApplicationContext.refresh()是所有故事的起点**：
```
1. prepareRefresh():    准备工作,记录开始时间,设置closed=false,active=true
2. obtainFreshBeanFactory():  创建DefaultListableBeanFactory,加载BeanDefinition
3. prepareBeanFactory():     配置BeanFactory的标准特性(ClassLoader/EventPublisher/Autowired)
4. postProcessBeanFactory(): 子类可重写(如ServletWebServerApplicationContext)
5. invokeBeanFactoryPostProcessors(): ⭐执行BeanDefinitionRegistryPostProcessor
   → ConfigurationClassPostProcessor: 解析@Configuration/@ComponentScan/@Import/@Bean
   → 这一步扫描所有类,注册所有BeanDefinition
6. registerBeanPostProcessors(): 注册BeanPostProcessor(Autowired/CommonAnnotation/Async)
7. initMessageSource():       国际化
8. initApplicationEventMulticaster(): 事件多播器
9. onRefresh():               子类特殊初始化(如创建内嵌Tomcat)
10. registerListeners():      注册监听器
11. finishBeanFactoryInitialization(): ⭐实例化所有非lazy单例Bean
    → 这一步创建所有Bean,解决依赖注入,触发@PostConstruct
12. finishRefresh():          发布ContextRefreshedEvent,初始化LifecycleProcessor
```

**架构师关键**：第5步(解析配置)和第11步(创建Bean)是refresh的核心。生产环境Spring启动慢→通常卡在第11步(Bean太多或某个Bean初始化耗时长)。

### 3.2 Bean生命周期

```
1. BeanDefinition注册 → 2. 实例化(beforeInstantiation) → 3. 构造函数创建对象
  → 4. 属性填充(@Autowired/@Value) → 5. Aware接口回调(BeanName/BeanFactory/ApplicationContext)
    → 6. BeanPostProcessor#postProcessBeforeInitialization → 7. @PostConstruct
      → 8. InitializingBean#afterPropertiesSet → 9. init-method
        → 10. BeanPostProcessor#postProcessAfterInitialization → 11. AOP代理生成
          → Bean就绪 → 12. DisposableBean#destroy → 13. @PreDestroy → 14. destroy-method
```

**架构师排查Bean问题**：
- Bean找不到→检查@ComponentScan范围/条件装配@Conditional
- 多个Bean候选→@Primary/@Qualifier/修改扫描范围
- Bean创建循环依赖→三级缓存解决(singletonObjects/earlySingletonObjects/singletonFactories)
- Bean初始化失败→检查@PostConstruct/afterPropertiesSet中是否有依赖未就绪

### 3.3 循环依赖与三级缓存

**三级缓存**：
```
singletonObjects:       一级缓存,存放完全初始化好的Bean
earlySingletonObjects:  二级缓存,存放提前暴露的早期Bean引用(半成品)
singletonFactories:     三级缓存,存放ObjectFactory→调用getObject()生成早期引用
```

**A↔B循环依赖解决流程**：
```
1. 创建A → 实例化A → 将A的ObjectFactory放入三级缓存 → 属性填充发现依赖B
2. 创建B → 实例化B → 将B的ObjectFactory放入三级缓存 → 属性填充发现依赖A
3. 从三级缓存获取A的ObjectFactory → getObject() → 生成A的早期引用(AOP代理或原始对象)
4. 将A的早期引用放入二级缓存 → B完成属性填充 → B放入一级缓存 → 删除B的二级/三级缓存
5. A完成属性填充(注入B) → A放入一级缓存 → 删除A的二级/三级缓存
```

**SpringBoot2.6+默认禁止循环依赖**：`spring.main.allow-circular-references=false`。架构师应该支持这个决定——循环依赖通常是设计问题，应该重构而非依赖Spring的hack解决。

### 3.4 事务传播机制与失效场景

**7种传播机制**：
```
REQUIRED:      默认,有事务加入,无事务新建(最常用)
SUPPORTS:      有事务加入,无事务非事务执行
MANDATORY:     必须在事务中,否则抛异常
REQUIRES_NEW:  总是新事务,挂起当前事务(内外事务独立)
NOT_SUPPORTED: 非事务执行,挂起当前事务
NEVER:         非事务执行,有事务则抛异常
NESTED:        嵌套事务(savepoint),外层回滚则内层也回滚,内层回滚外层不受影响
```

**事务失效7种场景**（架构师Checklist）：
```
1. 方法非public:     Spring AOP基于CGLIB/JDK代理,非public方法不被代理
2. 自调用(this.xx):  同类内方法调用不经过代理→事务不生效(最常见!)
3. 异常被catch:      catch吞掉异常→TransactionInterceptor看不到异常→不回滚
4. 异常类型不匹配:   默认只回滚RuntimeException,checked异常不回滚→需rollbackFor=Exception.class
5. 数据库不支持:     MySQL MyISAM不支持事务→需用InnoDB
6. 传播机制不当:     REQUIRES_NEW内层事务回滚不影响外层→可能不符合预期
7. 多线程:          事务信息存在ThreadLocal→多线程各自独立→不在同一事务中
```

## S4 数据库深水区

> 架构师视角：数据库是大多数系统的性能瓶颈和可靠性关键。架构师必须能做数据架构决策(分库分表/读写分离/选型)、性能调优(慢SQL/索引/参数)和容灾设计(主从复制/MGR/备份恢复)。

### 4.1 InnoDB架构

```
Buffer Pool(内存):
  ├── LRU List(改进LRU: young区5/8 + old区3/8)
  ├── Flush List(脏页列表,定期刷盘)
  ├── Free List(空闲页列表)
  ├── Adaptive Hash Index(自适应哈希索引,自动优化热点页)
  ├── Change Buffer(二级索引的变更缓冲,合并写入)
  └── Doublewrite Buffer(双写缓冲,防止页写一半断电)

磁盘:
  ├── System Tablespace(ibdata1): 双写缓冲+Change Buffer+回滚段
  ├── Redo Log(ib_logfile0/1): WAL,顺序写,崩溃恢复
  ├── Undo Log(5.7在ibdata1, 8.0可独立表空间): 事务回滚+MVCC
  └── 数据文件(.ibd): 每表独立表空间(默认innodb_file_per_table=ON)
```

**Buffer Pool改进LRU**：防止全表扫描的冷数据冲掉热数据。
```
传统LRU: 新页面放头部 → 全表扫描100万行 → 热数据全部被挤出
InnoDB LRU: 
  新页面放old区头部( midpoint, 5/8处)
  在old区存活超过innodb_old_blocks_time(默认1s) → 才移入young区头部
  → 全表扫描的冷数据只在old区,不会进入young区冲掉热数据
```

### 4.2 MVCC实现

**每行隐藏列**：
```
DB_TRX_ID:     最后修改(插入/更新)该行的事务ID(6字节)
DB_ROLL_PTR:   指向Undo Log中该行的上一个版本(7字节)
DB_ROW_ID:     隐藏自增ID(6字节,无主键时使用)
```

**ReadView**：
```
m_ids:         创建ReadView时当前活跃(未提交)的事务ID列表
m_min_trx_id:  m_ids中最小的事务ID
m_max_trx_id:  下一个将分配的事务ID(最大活跃ID+1)
m_creator_trx_id: 创建该ReadView的事务ID

可见性判断(version_trx_id为某版本的修改事务ID):
  1. version_trx_id == m_creator_trx_id → 自己修改的 → 可见
  2. version_trx_id < m_min_trx_id → 在ReadView创建前已提交 → 可见
  3. version_trx_id >= m_max_trx_id → 在ReadView创建后才开始 → 不可见
  4. m_min_trx_id <= version_trx_id < m_max_trx_id:
     在m_ids中 → 未提交 → 不可见
     不在m_ids中 → 已提交 → 可见
     不可见 → 沿DB_ROLL_PTR找上一个版本继续判断
```

**RC vs RR的本质区别**：
- RC：每次SELECT创建新ReadView→能看到其他已提交事务的最新修改→不可重复读
- RR：只在第一次SELECT创建ReadView→整个事务期间看到的是同一快照→可重复读

### 4.3 锁体系

**InnoDB锁层次**：
```
表级锁: 意向共享锁(IS) / 意向排他锁(IX) → 快速判断表中是否有行锁,避免逐行扫描
行级锁: 
  记录锁(Record Lock):   锁住索引上的某条记录
  间隙锁(Gap Lock):      锁住记录之间的间隙(防止幻读插入),不锁记录本身
  临键锁(Next-Key Lock):  = 记录锁 + 间隙锁, 锁住左开右闭区间
  插入意向锁(Insert Intention Lock): 插入时在间隙上设置的轻量级锁,不同事务插同一间隙不同位置不冲突
```

**加锁规则(RR隔离级别,架构师必须掌握)**：
```
1. 默认加Next-Key Lock(左开右闭)
2. 等值查询唯一索引且记录存在 → 退化为记录锁(只锁住匹配行)
3. 等值查询唯一索引但记录不存在 → 退化为间隙锁(锁住间隙,防插入)
4. 等值查询非唯一索引 → Next-Key Lock(匹配行) + 间隙锁(下一个行前的间隙)
5. 范围查询 → 扫描到的每个索引加Next-Key Lock
```

### 4.4 分库分表方案设计

**ShardingSphere架构**：
```
应用层:    ShardingSphere-JDBC(嵌入式JAR,应用内路由) → 推荐,性能好
代理层:    ShardingSphere-Proxy(独立代理服务,数据库协议) → 跨语言/异构系统

核心概念:
  分片键(Sharding Key):    路由依据(如user_id)
  分片算法:                精确分片/范围分片/复合分片
  广播表:                  每个库全量(字典表/配置表)
  绑定表:                  相同分片键的分表(如order+order_item都按user_id分)
```

**架构师决策路径**：
```
单表数据量 > 500万 或 单表容量 > 2GB → 考虑分库分表
  先考虑: 能否加索引? 能否归档历史数据? 能否读写分离?
  → 最后才分库分表

分片键选择原则:
  1. 数据分布均匀(避免热点)
  2. 尽量是查询条件(避免全分片扫描)
  3. 关联表用相同分片键(避免跨库JOIN)

代价:
  - 跨库JOIN困难 → 需代码层组装 或 冗余字段
  - 分布式事务 → 需Seata/本地消息表
  - 全局唯一ID → 需Snowflake/Leaf
  - 扩容困难 → 需双写迁移 或 一致性哈希
  - 运维复杂 → 监控/备份/DDL变更需覆盖所有分片
```

### 4.5 CDC(Change Data Capture)

**Canal工作原理**：
```
1. Canal Server伪装成MySQL Slave,向Master发送Binlog Dump请求
2. Master推送Binlog事件给Canal
3. Canal解析Binlog(INSERT/UPDATE/DELETE) → 转为结构化数据
4. 投递到下游( Kafka/RocketMQ/直接回调 )

支持模式:
  - ROW模式: 记录每行变更的完整数据(推荐,数据最完整)
  - STATEMENT模式: 记录SQL语句(数据量小但可能有不确定性)
  - MIXED模式: 混合
```

**架构师典型应用**：
```
缓存一致性:    MySQL → Canal → 更新Redis (比延迟双删更可靠)
ES索引同步:    MySQL → Canal → 写入ES (比双写更解耦)
数据迁移:      全量(dump) + 增量(Canal) 迁移方案
审计日志:      MySQL → Canal → 审计系统 (记录所有数据变更)
数据订阅:      MySQL → Canal → Kafka → Flink (实时数据处理)
```
