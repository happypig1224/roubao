## S5 缓存与搜索深水区

### 5.1 Redis底层数据结构演进

**Redis对外5种类型 → 底层多种编码，根据数据量自动选择最优实现**：

```
String:  SDS(简单动态字符串)
         embstr(≤44字节,一次分配,紧凑) → raw(>44字节,两次分配)
         
List:    listpack(Redis 7.0,替代ziplist) → quicklist(listpack+双向链表)
         历史版本: ziplist(元素少+小) → linkedlist(元素多)
         
Hash:    listpack(field/value对少+小) → hashtable(元素多)
         历史版本: ziplist → hashtable
         
Set:     intset(全是整数且元素少) → listpack(元素少+小) → hashtable(元素多)
         
ZSet:    listpack(member+score对少+小) → skiplist+hashtable(元素多)
         skiplist: 按score有序,支持范围查询
         hashtable: 按member查找,支持O(1)判断成员存在
```

**listpack vs ziplist**（Redis 7.0重大变更）：
```
ziplist问题: 
  - 中间元素修改可能引发级联更新(cascade update)→最坏O(N²)
  - 元素长度用1/2/5字节编码,5字节编码时prevlen字段浪费空间
  
listpack优化:
  - 不存储前一个节点长度→消除级联更新
  - 每个元素自身记录总长度→解析更简单
  → Redis 7.0全面用listpack替代ziplist
```

### 5.2 Redis持久化与生产选择

| 方案 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| RDB | fork子进程→遍历内存→写临时文件→rename替换 | 恢复快(直接加载)、文件紧凑 | 非实时(两次save间数据可能丢)、fork耗内存( Copy-On-Write) | 备份/跨机房同步 |
| AOF | 追加写命令→重写(合并冗余命令) | 数据更安全(每秒fsync最多丢1秒) | 文件大、恢复慢、重写耗CPU | 数据安全要求高 |
| 混合(4.0+) | AOF重写时前半段用RDB格式,后半段用AOF | 兼顾恢复速度+数据安全 | 配置复杂 | 生产推荐 |

**生产配置建议**：
```
# 混合持久化(推荐)
appendonly yes
appendfsync everysec        # 每秒fsync,最多丢1秒数据
aof-use-rdb-preamble yes   # AOF重写时前半段用RDB

# RDB作为备份(定时生成)
save 900 1                  # 15分钟至少1个key变更
save 300 10                 # 5分钟至少10个key变更
save 60 10000               # 1分钟至少10000个key变更
```

### 5.3 Redis Cluster生产部署

**16384槽分配**：
```
cluster-node-id:   40字符的节点唯一ID
slot分配:          cluster addslots {0..5460} 给主节点1
                  cluster addslots {5461..10922} 给主节点2
                  cluster addslots {10923..16383} 给主节点3
路由:              slot = CRC16(key) & 16383
```

**Gossip协议通信**：
```
每个节点每秒随机选5个其他节点发送ping(携带自身状态+部分其他节点状态)
→ 节点故障检测: 超过cluster-node-timeout未收到pong→标记pfail(疑似故障)
→ 超过半数主节点确认pfail→标记fail(确定故障)→从节点发起选举
```

**生产部署建议**：
```
主节点: 3-9个(奇数便于选举,不宜过多,Gossip通信开销O(N))
从节点: 每主节点至少1个从(推荐2个,保证1个故障仍能选举)
内存:   单节点建议≤10GB(fork RDB时COW占用物理内存)
部署:   主从分散在不同物理机/机架(避免整机/整架故障)
客户端: Lettuce/JedisCluster(Smart客户端,缓存slot→node路由表)
```

### 5.4 分布式锁(Redis vs ZK)

**Redisson RLock实现**：
```java
// 加锁(Lua脚本保证原子性)
// KEYS[1]=锁名, ARGV[1]=TTL(ms), ARGV[2]=clientId+threadId
if (redis.call('exists', KEYS[1]) == 0) then
    redis.call('hset', KEYS[1], ARGV[2], 1)     // Hash存储: 锁名→(持有者→重入次数)
    redis.call('pexpire', KEYS[1], ARGV[1])      // 设置TTL
    return nil
end
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then  // 同一持有者→可重入
    redis.call('hincrby', KEYS[1], ARGV[2], 1)   // 重入次数+1
    redis.call('pexpire', KEYS[1], ARGV[1])       // 续期
    return nil
end
return redis.call('pttl', KEYS[1])               // 返回剩余TTL,加锁失败
```

**看门狗(Watchdog)续期**：
```
默认leaseTime=30秒 → 每隔30/3=10秒检查锁还被当前线程持有 → 续期到30秒
如果业务执行超过30秒且看门狗正常 → 锁不会过期(自动续期)
如果持有锁的客户端宕机 → 看门狗停止 → 30秒后锁自动过期释放
```

**Redlock争议**（架构师必须了解）：
```
antirez(Redis作者): Redlock算法→5个独立Redis实例→多数加锁成功→安全
Martin Kleppmann:   Redlock不安全→时钟跳跃/进程暂停(GC STW)可能导致锁过期后仍认为持有
                    → 推荐用ZK/etcd(基于租约+fencing token)

架构师判断: 
  - 大部分业务场景: Redisson单实例锁够用(加fencing token更安全)
  - 金融核心场景: 用ZK锁(CP保证)或数据库悲观锁
  - 不要用Redlock(过度工程化且争议未定)
```

```
搜索"架构师" → 查倒排索引 → [文档1, 文档2] → BM25评分排序 → 返回结果
```

**写入流程**（架构师必须理解）：
```
1. 文档写入 → 写入内存Indexing Buffer + 写入Translog(预写日志)
2. Refresh(默认1秒): Buffer → 新Segment(可搜索但未持久化) → 清空Buffer
3. Flush(默认30分钟/Translog达512MB): Segment → 磁盘 + 清空Translog
4. Merge(后台): 小Segment合并为大Segment → 减少Segment数量+删除已标记删除的文档

关键理解:
  - 写入后约1秒可搜索(Refresh间隔)→ES是近实时搜索
  - Translog保证未Flush的数据不丢(崩溃恢复用)
  - Merge是IO密集型→大量写入时可能影响查询性能→控制merge线程数和速率
```

**集群架构**：
```
主节点(Master):   管理集群状态(不存数据), 建议3个(避免脑裂)
数据节点(Data):   存储索引数据+执行CRUD, 根据数据量规划
协调节点(Coordinating): 不存数据,只做请求路由+结果合并(类似网关)
冷热节点:          热节点(SSD,存近期数据) + 冷节点(HDD,存历史数据)

分片策略:
  - 主分片数: 创建索引后不可修改→需提前规划(按数据量/节点数)
  - 副本分片数: 可动态调整→提高可用性+查询并发度
  - 经验: 单分片10-50GB, 分片数=数据量/单分片大小
```

## S6 分布式理论基础

> **这是整个架构师路线中最重要的阶段。** 不理解分布式理论，你用的微服务/中间件/高可用方案都是"照猫画虎"。

### 6.1 CAP定理深度理解

**证明思路**（架构师应该能推导，不只是背结论）：
```
假设N1和N2两个节点,网络分区(N1↔N2断开)

场景1: 保证C(一致性)
  → 写入N1后,N2必须返回最新值 → 需要同步N2 → 但网络断开无法同步
  → N2要么返回旧值(违反C),要么拒绝服务(违反A)

场景2: 保证A(可用性)
  → N1和N2都正常响应 → 但无法同步 → 可能返回不一致数据(违反C)

结论: 网络分区发生时,C和A不可能同时满足
```

**AP vs CP系统**：
```
CP系统(保证一致性,牺牲可用性):
  ZK:       Leader选举期间不可用(约30s),但数据不丢
  ETCD:     Leader故障期间读写阻塞,但数据强一致
  HBase:    RegionServer故障期间该Region不可用
  TiKV:     Raft协议,Leader切换期间不可用

AP系统(保证可用性,牺牲一致性):
  Eureka:   节点间不复制,每个节点独立服务,可能返回过期注册信息
  Nacos临时实例: Distro协议,最终一致,分区时各节点独立服务
  Cassandra: 读写走最近节点,用Hinted Handoff补偿,最终一致

可切换:
  Nacos: 临时实例(AP,Distro) + 持久实例(CP,Raft) → 根据业务选择
```

**架构师设计原则**：同一个系统内部可以混合——核心链路(支付/库存)用CP，非核心链路(评论/推荐)用AP。

### 6.2 Raft协议深度

**Leader选举**：
```
初始状态: 所有节点都是Follower,有electionTimeout(150-300ms随机)

1. Follower超时未收到Leader心跳 → 转为Candidate
2. Candidate: term++, 投自己一票, 向所有节点发RequestVote RPC
3. 收到多数票(n/2+1) → 成为Leader
4. 立即发心跳(AppendEntries, term, 空entry) → 阻止其他选举

选举约束(安全性关键):
  - 每个term最多一个Leader(过半投票保证)
  - Candidate的日志至少和投票者一样新 → 新Leader包含所有已Commit的日志
```

**日志复制**：
```
Client写请求 → Leader追加日志entry → 发AppendEntries给所有Follower
  → 多数Follower确认 → Leader Commit → 响应Client

AppendEntries一致性检查:
  prevLogIndex和prevLogTerm → Follower检查本地是否有相同index和term的日志
  → 匹配则追加 → 不匹配则拒绝 → Leader回退nextIndex重试
```

**架构师锚定**：Nacos CP模式、ETCD、TiKV、Consul都用Raft。理解Raft → 理解这些系统在Leader切换时的行为(短暂不可用但数据不丢)。

### 6.3 分布式事务深度对比

**2PC/XA(Seata AT模式)**：
```
阶段1(Prepare): 
  TC(事务协调者) → 所有RM(资源管理者)执行SQL但不提交
  → RM生成Undo Log(反向SQL) → 返回Yes
  
阶段2(Commit): 
  TC → 所有RM提交 → 异步删除Undo Log

阶段2(Rollback):
  TC → 所有RM根据Undo Log回滚 → 删除Undo Log

Seata AT优势: 对业务无侵入(只需加@GlobalTransactional)
Seata AT代价: 
  - 需要Undo Log表(每个业务库一张)
  - 全局锁(防止脏写) → 可能和本地事务冲突
  - TC单点风险 → 需集群部署
```

**TCC(Seata TCC模式)**：
```
Try:    资源检查+预留(如冻结金额)
Confirm: 确认操作(如扣减冻结金额) → 必须幂等
Cancel:  取消操作(如解冻金额) → 必须幂等

与AT的区别:
  AT: 框架自动生成Undo Log → 对业务无侵入 → 但有全局锁
  TCC: 业务手写Try/Confirm/Cancel → 有侵入 → 但无全局锁,性能更好
  
适用: 资金/库存等强一致性+高并发场景(全局锁代价不可接受时)
```

**Saga(Seata Saga模式)**：
```
正向: T1(创建订单) → T2(扣库存) → T3(扣余额) → T4(发通知)
反向: C3(恢复余额) → C2(恢复库存) → C1(取消订单)   (T3失败时)

适用: 长事务(如旅行预订: 机票+酒店+租车,耗时数秒到数分钟)
代价: 不保证隔离性 → 可能出现脏读 → 需要业务层补偿
```

**本地消息表(最实用的方案)**：
```
1. 业务操作 + 写入本地消息表 → 在同一个本地事务中(强一致)
2. 后台线程定时扫描消息表 → 发送到MQ
3. 消费者消费MQ → 执行远程操作 → 成功则更新消息状态

优势: 不依赖Seata TC → 实现简单 → 生产最常用
代价: 需要消息表 → 需要定时扫描线程 → 消息可能有延迟
```

**架构师选型决策树**：
```
是否需要强一致?
  是 → 并发<1000? → Seata AT(简单) : TCC(高性能)
  否 → 可接受最终一致? 
    是 → 长事务? → Saga : 本地消息表+MQ(推荐)
    否 → 重新评估业务需求
```

## S7 分布式中间件体系

### 7.1 API网关选型

**架构师选型维度**：
```
1. 性能: QPS/延迟/内存占用
2. 功能: 认证鉴权/限流熔断/灰度发布/协议转换/日志监控
3. 扩展性: 插件机制/自定义Filter/多语言支持
4. 运维: 配置中心集成/动态路由/监控指标/部署方式
5. 团队: 语言栈/运维经验/社区活跃度
```

**Spring Cloud Gateway核心架构**：
```
请求 → DispatcherHandler → RoutePredicateHandlerMapping(路由匹配)
     → FilteringWebHandler(过滤器链) → 代理到下游服务 → 响应

核心Filter:
  - AddRequestHeader/AddResponseHeader: 头部增删改
  - PrefixPath/StripPrefix: 路径重写
  - RequestRateLimiter: 限流(需KeyResolver+RedisRateLimiter)
  - CircuitBreaker: 熔断(集成Resilience4J/Sentinel)
  - RewritePath: 路径重写
```

### 7.2 Kafka核心架构

**Kafka为什么快？**
```
1. 顺序写: 消息追加到Partition末尾 → 磁盘顺序写速度≈600MB/s(接近内存)
2. 零拷贝: Consumer用sendfile()直接从文件→网卡 → 无用户态拷贝
3. 页缓存: 数据先写OS Page Cache → 由OS异步刷盘 → 写入即返回
4. 批处理: 生产者批量发送,消费者批量拉取 → 减少网络IO次数
5. 分区并行: 多Partition并行读写 → 水平扩展
6. 压缩: 生产者压缩(减少网络传输),消费者解压
```

**Kafka vs RocketMQ架构对比**：
```
存储:
  Kafka:   Partition=一个目录,多个Segment文件(稀疏索引)
  RocketMQ: CommitLog(所有topic共用一个文件,顺序写) + ConsumeQueue(逻辑队列索引)

消费者模型:
  Kafka:   Consumer Group + Rebalance(分区分配给消费者)
           Rebalance问题: 消费者变化时全量重新分配 → 可能触发Stop The World
  RocketMQ: 每个Consumer分配MessageQueue → 无Rebalance问题

消息可靠性:
  Kafka:   副本同步(ISR) + Leader Epoch → 防止数据不一致
  RocketMQ: 同步双写/异步刷盘 + 主从复制 → 更灵活的可靠性配置
```

## S8 微服务源码与Dubbo3

### 8.1 Nacos源码核心

**注册中心源码入口**：
```
客户端:
  NamingService.registerInstance()
    → grpcClient.requestToServer() / httpClient.post()
      → InstanceController.register()  (服务端入口)
      
服务端:
  InstanceController.register()
    → serviceManager.registerInstance()
      → putInstance() → 内存注册表更新
      → notifier.publishEvent() → 通知订阅者
      
集群同步(Distro协议,AP模式):
  每个节点负责一部分服务的注册信息(按hash分配)
  → 节点启动时从其他节点同步自己负责的部分
  → 注册信息变更时,只同步给负责该服务的节点
  → 所有节点都有全量数据的只读副本
```

### 8.2 Sentinel源码核心

**Slot Chain流程**：
```
请求进入 → SphU.entry("resourceName")
  → ProcessorSlotChain.entry()
    → NodeSelectorSlot:     创建ClusterNode(统计节点)
    → ClusterBuilderSlot:   构建集群统计节点
    → LogSlot:              记录日志
    → StatisticSlot:        ⭐统计QPS/RT/线程数(滑动窗口LeapArray)
    → FlowSlot:             ⭐流控检查(对比规则与统计值)
    → DegradeSlot:          ⭐熔断检查(根据统计值判断是否熔断)
    → SystemSlot:           系统保护(CPU/Load/RT/线程数)
    → AuthoritySlot:        授权检查(黑白名单)
  → 业务逻辑执行
  → SphU.exit()
    → StatisticSlot:        记录RT(耗时)
```

**LeapArray滑动窗口**：
```
时间窗口划分: 将1秒划分为500ms的2个窗口(默认sampleCount=2, intervalInMs=1000)
每个WindowWrap: windowStart + MetricBucket(计数器: pass/block/rt/exception/success)
当前时间 → 计算窗口索引 → 获取对应WindowWrap → 累加计数

流控判断: 当前窗口pass数 > 流控阈值 → 拒绝
熔断判断: 当前窗口exception比例 > 熔断阈值 → 熔断
```

### 8.3 Dubbo3 Triple协议

**Triple vs Dubbo协议**：
```
Dubbo协议(Dubbo2默认):
  - 自定义TCP二进制协议: Magic(2B) + Flag(1B) + Status(1B) + RequestID(8B) + DataLength(4B) + Body
  - 基于Hessian2序列化
  - 问题: 非标准协议,跨语言困难(需各语言SDK)

Triple协议(Dubbo3默认):
  - 基于HTTP/2 + ProtoBuf(Protocol Buffers)
  - 兼容gRPC协议格式
  - 支持4种流式RPC:
    Unary:            请求-响应(最常用,等价于普通RPC)
    ServerStream:     请求-流式响应(服务端推送,如订阅)
    ClientStream:     流式请求-响应(客户端上传流,如文件上传)
    BidiStream:       双向流(如聊天)
  - 优势: 跨语言(任何支持HTTP/2的语言都能调用),流式,标准协议
```

## S9 高可用与高并发架构

> **这是架构师和高级开发的分水岭。** 高级开发知道怎么用限流/熔断/降级，架构师知道整个高可用体系如何组合、什么场景用什么策略、各策略的代价是什么。

### 9.1 限流体系全景

**四种算法数学原理**：

```
固定窗口: window_count / window_size ≤ threshold
  问题: 窗口边界2倍突刺(0.9秒无请求+0.1秒2*threshold请求→通过但瞬时超限)

滑动窗口: 任意时间区间[tn-1, tn]的count ≤ threshold * (tn-tn-1) / window_size
  解决: 固定窗口的边界问题,但内存开销更大(需存储每个子窗口计数)

令牌桶: 以rate速率往桶里放令牌,请求取1个令牌,桶满丢弃新令牌
  特性: 允许突发(桶内累积的令牌可一次性取走) → 适合"允许短时突发"的场景
  公式: available_tokens = min(capacity, prev_tokens + (now-prev)*rate)

漏桶: 请求进桶排队,以固定速率出桶(处理)
  特性: 流量平滑(强制匀速) → 适合"严格匀速"的场景(如调用第三方API)
```

**集群限流方案**：
```
1. 中心化: 所有请求到Redis执行Lua脚本 → 精确但依赖Redis可用性
2. Token Server(Sentinel集群限流): 专门节点分配token → 减轻Redis压力
3. 网关层限流: Nginx/Kong/Gateway层限流 → 拦截在入口,保护内部服务
4. 自适应限流(BBR): 根据系统负载(CPU/队列)自动调节限流阈值 → 无需配置阈值
```

### 9.2 熔断降级体系

**断路器状态机**：
```
         成功率恢复
  Open ──────────→ Half-Open
   ↑                  │  │
   │ 探测失败         │  │ 探测成功
   │                  ↓  ↓
   └──────────── Closed ←─┘
   
Closed:  正常放行,统计失败率/慢调用率
Open:    直接拒绝/走降级,启动冷却计时器(如10秒)
Half-Open: 冷却结束,放少量请求(如5个)探测
  → 全部成功 → 回Closed
  → 仍有失败 → 回Open
```

**降级策略设计**（架构师必须为每个服务设计降级预案）：
```
返回默认值:     适合读操作(如推荐列表为空时返回热门列表)
走兜底数据:     适合核心读操作(如商品详情→读缓存中的历史数据)
写缓存后重试:   适合写操作(先写本地缓存→异步重试→保证最终一致)
关闭非核心功能:  适合高负载时(如关闭评论/推荐/搜索,保留核心购买流程)
读降级:         从实时数据降级为缓存数据(如库存实时→缓存库存)
写降级:         从同步写降级为异步写(如日志/通知改为MQ异步)
```

### 9.3 超时级联与重试风暴

**超时设置原则**：
```
全链路超时级联:
  网关(3s) > 服务A(2s) > 服务B(1.5s) > 服务C(1s) > DB(500ms) > Redis(100ms)
  
为什么上游>下游之和? 
  避免上游已超时返回,下游还在处理(浪费资源+可能导致数据不一致)

P99/P999超时:
  不要用平均RT设置超时 → 用P99甚至P999 → 保证99%/99.9%请求在超时内完成
  例: P99=200ms → 设置超时=200*2=400ms(2倍P99留余量)
```

**重试规范**（架构师必须制定团队规范）：
```
1. 幂等保障:  写操作必须幂等(用唯一请求ID+Redis去重)
2. 退避策略:  指数退避+随机抖动 → 避免所有请求同时重试(Thundering Herd)
              delay = baseDelay * 2^retryCount + random(0, baseDelay)
3. 重试次数:  通常1-3次,不要无限重试
4. 可重试异常: 仅对网络超时/503等可恢复异常重试,不对400/500等业务异常重试
5. 重试监控:  重试率=重试次数/总请求数,>5%需关注→可能是下游有问题
```

### 9.4 多活架构

**演进路线**：
```
冷备机房:       平时不服务,故障时切换DNS → RTO(恢复时间)30分钟+,数据可能丢
同城双活:       两机房同时服务,流量50:50,数据双向同步 → RTO秒级
异地多活:       跨城市部署(北京+上海+深圳),数据异地同步 → RTO秒级,容灾城市级
单元化架构:     每个单元(机房)独立闭环,数据按用户ID路由到固定单元 → 从根本上解决数据同步冲突
```

**数据同步难题与解决方案**：
```
问题: 同一条数据在两个机房同时修改 → 冲突如何解决?
  - 最后修改胜出(LWW): 简单但可能丢数据
  - 应用层合并: 复杂但精确
  - 避免冲突: 单元化(每条数据只属于一个单元,只在所属单元修改)

支付宝单元化架构(业界标杆):
  - 按用户ID分单元: user_id % 单元数 = 单元ID
  - 每个单元部署全套服务+数据库
  - 同一用户的所有请求路由到同一单元
  - 单元间无数据共享 → 无同步冲突
  - 单元故障 → 流量切换到其他单元(该单元用户短暂不可用)
```

### 9.5 灰度发布体系

**三种灰度策略**：
```
蓝绿部署(Blue-Green):
  两套完整环境(蓝/绿) → 新版本部署到空闲环境 → 切流量 → 有问题切回
  优点: 回滚极快(切流量即可)
  缺点: 需要双倍资源

金丝雀发布(Canary):
  新版本先部署1台 → 导入5%流量 → 观察 → 逐步扩大到100%
  优点: 资源节省+渐进验证
  缺点: 回滚需重新部署

特性开关(Feature Toggle):
  代码中if(toggle.isEnabled()) → 新老逻辑共存 → 开关控制走哪个
  优点: 无需部署即可切换 → 适合A/B测试
  缺点: 代码分支增多 → 需要定期清理过期开关
```

**全链路灰度**(微服务灰度的核心挑战)：
```
问题: 只在网关层灰度不够 → 下游服务调用的还是老版本 → 不是真正的全链路灰度

解决方案: 标签路由+流量染色
  1. 网关层: 灰度用户请求打上gray标签(Header/Attachment)
  2. Dubbo/Sentinel: 标签路由 → 灰度请求路由到灰度节点
  3. RPC调用: 标签透传(RpcContext设Attachment) → 下游也路由到灰度节点
  4. 数据隔离: 灰度流量写灰度库/灰度缓存 → 不污染生产数据
```

### 9.6 容灾与混沌工程

**Chaos Engineering**（架构师的高级认知）：
```
核心思想: 主动注入故障 → 验证系统韧性 → 发现薄弱环节 → 加固

实践步骤:
  1. 定义稳态假设: "系统正常时P99延迟<200ms"
  2. 引入故障: 关掉一个节点/增加200ms延迟/丢掉50%网络包
  3. 观察稳态: 系统是否仍满足假设? 
  4. 改进: 不满足 → 修复 → 再验证

工具:
  Chaos Mesh(K8s):    Pod Kill / Network Delay / IO Fault / Stress
  Litmus(云原生):     Chaos工程平台
  Gremlin(商业):      SaaS平台

大厂实践:
  - Netflix: Chaos Monkey(随机杀实例)→ Chaos Kong(随机杀整个可用区)
  - 阿里: 每月"安全生产日"全链路故障演练
  - 美团: 自动化故障注入+指标监控+自动恢复
```
