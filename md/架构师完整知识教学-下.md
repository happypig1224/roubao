## S10 云原生与Kubernetes

> 架构师视角：云原生不是"用Docker部署"，而是一整套方法论——容器化+微服务+声明式API+不可变基础设施+自动伸缩+GitOps。K8s是云原生的操作系统。

### 10.1 K8s核心对象详解

**Pod生命周期**：
```
Pending → ContainerCreating → Running → Succeeded/Failed
                                    ↘ CrashLoopBackOff(容器反复崩溃重启)

Pod内容器重启策略: Always(默认) / OnFailure / Never
Pod驱逐策略:      nodefs.available<15% 或 imagefs.available<15% → kubelet驱逐Pod
```

**Deployment滚动更新**：
```
.spec.strategy.type: RollingUpdate(默认)
.spec.strategy.rollingUpdate.maxSurge:       滚动更新时最多多出几个Pod(默认25%)
.spec.strategy.rollingUpdate.maxUnavailable: 滚动更新时最多不可用几个Pod(默认25%)

流程: 创建新ReplicaSet → 逐步扩新Pod+缩旧Pod → 全部替换完成
回滚: kubectl rollout undo deployment/xxx --to-revision=N
```

**Service类型**：
```
ClusterIP:    集群内虚拟IP(默认,仅集群内可达)
NodePort:     每个Node开一个端口(30000-32767),外部可访问
LoadBalancer: 云厂商LB(如阿里云SLB),外部流量→LB→NodePort→Pod
ExternalName: CNAME别名,指向集群外部服务(如外部MySQL)
```

**Ingress vs Gateway API**：
```
Ingress(旧):
  - 基于HTTP/HTTPS路由
  - 需要Ingress Controller(Nginx/Traefik)实现
  - 配置: host+path → Service

Gateway API(新, K8s 1.24+):
  - 更灵活: GatewayClass → Gateway → HTTPRoute
  - 支持多团队协作(集群管理员定义GatewayClass, 集群运维定义Gateway, 应用开发定义Route)
  - 更好的扩展性
```

### 10.2 Helm与GitOps

**Helm Chart结构**：
```
mychart/
  ├── Chart.yaml          # 元数据(name/version/description)
  ├── values.yaml         # 默认配置值
  ├── templates/
  │   ├── deployment.yaml # Deployment模板(引用values中的变量)
  │   ├── service.yaml    # Service模板
  │   ├── ingress.yaml    # Ingress模板
  │   └── _helpers.tpl    # 模板辅助函数
  └── .helmignore         # 忽略文件
```

**ArgoCD GitOps工作流**：
```
1. 开发者提交代码 → CI构建镜像 → 推送镜像仓库
2. 更新Git仓库中的K8s清单(Helm values/kustomize) → Git Push
3. ArgoCD检测到Git变更 → 自动Sync到K8s集群 → 部署完成
4. ArgoCD持续Drift Detection → 集群状态偏离Git → 自动/手动纠正

核心理念: Git是唯一真相源 → 所有变更必须通过Git → 可审计/可回滚/可复现
```

### 10.3 Service Mesh(Istio)

**Istio架构**：
```
控制面(istiod):
  - Pilot:     服务发现+流量管理规则下发
  - Citadel:   证书管理(mTLS)
  - Galley:    配置验证

数据面(Envoy Sidecar):
  - 每个Pod注入一个Envoy容器
  - 拦截所有入站+出站流量
  - 根据控制面下发的规则执行: 路由/重试/超时/熔断/流量分割/mTLS

代价:
  - 每Pod增加约100MB内存(Envoy) + 2-5ms延迟(两次Sidecar拦截)
  - 运维复杂度增加(需理解Istio配置+Envoy行为)
  - Sidecar管理(升级/故障/资源)

适用判断:
  - 服务数>50 + 多语言 + 需要统一流量治理 → Istio有价值
  - 服务数<20 + 纯Java生态 → Spring Cloud Sentinel/Gateway更简单
```

## S11 可观测性与DevOps

> 架构师视角：可观测性是生产环境的生命线。没有可观测性的系统上线=盲人开高速。

### 11.1 可观测性三支柱深度

**Metrics(Prometheus+Grafana)**：
```
四种指标类型:
  Counter:    只增不减(如请求总数、错误总数) → 适合算速率(rate())
  Gauge:      可增可减(如当前在线用户数、CPU使用率) → 适合画趋势图
  Histogram:  分布统计(如请求延迟分布) → 适合算P50/P95/P99
  Summary:    客户端预计算分位数 → 精确但不可聚合 → 少用

PromQL关键查询:
  rate(http_requests_total[5m])               # 5分钟平均QPS
  histogram_quantile(0.99, rate(http_latency_bucket[5m]))  # P99延迟
  sum(rate(http_requests_total{status="500"}[5m])) 
    / sum(rate(http_requests_total[5m]))       # 错误率

Java集成: Micrometer → Spring Boot Actuator → Prometheus抓取 → Grafana可视化
```

**Tracing(SkyWalking)**：
```
核心概念:
  Trace:  一次完整请求的调用链(跨多个服务)
  Span:   一次服务调用(有parentSpanId组成树形结构)
  Segment: 一个线程内的Span集合

Java Agent原理:
  启动时: -javaagent:skywalking-agent.jar
  → 字节码增强: 修改Spring MVC/Dubbo/Redis/MySQL等的入口方法
  → 方法执行前: 创建Span + 记录startTime
  → 方法执行后: 记录endTime + 上报到OAP Server

跨服务传播:
  RPC调用时在Header/Attachment中注入TraceContext(sw8/sw8-correlation)
  → 下游服务从Header提取 → 继续同一个Trace
```

**三支柱关联**：
```
发现异常:  Metrics告警(P99延迟>500ms)
定位问题:  Tracing找到慢Span(数据库查询耗时400ms)
查看详情:  Logging用TraceId搜索该请求的所有日志

实现关联:
  - 所有日志打印TraceId(MDC/Slf4j)
  - Metrics标签带TraceId(可选)
  - Tracing的Span带业务标签(userId/orderId)
```

### 11.2 告警体系设计

**告警分级(架构师必须定义)**：
```
P0(紧急):  核心服务不可用/数据丢失/安全漏洞 → 5分钟内响应 → 电话+短信
P1(高):    核心功能降级/性能严重下降 → 30分钟内响应 → 短信+IM
P2(中):    非核心功能异常/性能轻微下降 → 当日处理 → IM
P3(低):    容量预警/优化建议 → 排期处理 → 邮件
```

**告警收敛策略**(防止告警风暴)：
```
分组(group_by):      同类告警聚合(如同一服务的所有实例CPU高→一条告警)
抑制(inhibit):       P0告警抑制P1(如服务不可用→不再报接口超时)
静默(silence):       计划内变更期间静默相关告警
去重(group_wait):    同一告警5分钟内不重复发送
频率限制(group_interval): 同一告警组4小时内最多发3次
```

**告警设计原则**：
```
1. P0告警宁可误报不可漏报(误报代价=被打扰, 漏报代价=业务中断)
2. 每条告警必须有Action(没有Action的告警是噪音→删除)
3. 告警必须有Runbook(操作手册→新人也知道怎么处理)
4. 告警必须有Owner(没有人认领的告警→等于没有告警)
5. 定期清理无用告警(告警疲劳→P0也可能被忽视)
```

## S12 大数据与流计算

> 架构师视角：你不需要成为大数据专家，但必须理解数据架构——什么时候需要Flink、数据湖解决什么问题、OLAP引擎怎么选。这是MCA 2026路线相比图灵路线新增的核心内容。

### 12.1 Flink核心架构

**四层架构**：
```
API层:      DataStream API(流) / Table API&SQL(表)
运行时层:   JobManager(调度+协调) + TaskManager(执行)
状态层:     State Backend(Heap/RocksDB) + Checkpoint(快照)
网络层:     Netty + 自定义网络栈(ResultPartition/InputGate)
```

**状态管理**(流计算最核心的难题)：
```
Keyed State:   按key分区,每个key独立状态(如每用户的点击计数)
Operator State: 算子级状态(如Kafka Source的offset)

状态后端选择:
  MemoryStateBackend:   状态存JVM堆 → 快但受GC影响,状态<5MB
  FsStateBackend:       状态存本地文件+Checkpoint存HDFS → 状态可达GB级
  RocksDBStateBackend:  状态存RocksDB(磁盘+LSM树) → 状态可达TB级,生产推荐
```

**Checkpoint机制**(Exactly-Once的保障)：
```
基于Chandy-Lamport算法的分布式快照:
1. JobManager定期向所有Source注入Checkpoint Barrier(n)
2. Barrier随数据流流动 → 算子收到Barrier → 将当前状态快照存到State Backend
3. 所有算子完成快照 → JobManager确认Checkpoint完成
4. 故障恢复 → 从最近成功的Checkpoint恢复状态 → 重新消费Source → 保证Exactly-Once

两阶段提交(2PC,用于Kafka Exactly-Once):
  Checkpoint开始 → 预提交(Kafka事务开始) → Checkpoint完成 → 正式提交
```

**Watermark机制**(乱序数据处理)：
```
事件时间(Event Time):  事件发生的时间(数据中携带)
处理时间(Process Time): Flink处理事件的时间

Watermark = max_event_time - allowed_lateness
  → Watermark是一种时间戳,表示"在此时间之前的数据应该都到了"
  → Watermark到达窗口结束时间 → 触发窗口计算

迟到数据处理:
  1. 正常处理: Watermark到达时计算
  2. 允许迟到: allowedLateness(Duration) → Watermark超过窗口后还允许等一段时间
  3. 侧输出: 超过允许迟到时间的数据 → 侧输出流(可人工处理或告警)
```

### 12.2 OLAP引擎选型

| 维度 | ClickHouse | Apache Doris | StarRocks |
|------|-----------|-------------|-----------|
| 定位 | 单表查询极快的OLAP | 实时+批处理一体OLAP | Doris分支,向量化和CBO增强 |
| 单表查询 | 极快(列存+向量化+MergeTree) | 快 | 快 |
| 多表JOIN | 弱(需大宽表) | 强(支持多种JOIN) | 最强(CBO+Runtime Filter) |
| 实时写入 | 弱(部分MergeTree支持) | 强(支持实时写入+更新) | 强 |
| 物化视图 | 支持 | 支持 | 支持 |
| 运维 | 单机简单,集群复杂 | 较简单(FE+BE) | 较简单 |
| 适用 | 日志分析/大宽表查询/实时大盘 | 报表/实时数仓/多维分析 | 报表/实时数仓(多表JOIN场景) |

**架构师选型**：单表场景/日志分析→ClickHouse；需要多表JOIN/实时写入→Doris/StarRocks。

### 12.3 数据湖与湖仓一体

**传统数仓 vs 数据湖 vs 湖仓一体**：
```
传统数仓:  结构化数据 + 预定义Schema + ETL → 写时模式 → 查询快但灵活性差
数据湖:    所有数据(结构+半结构+非结构) + Schema on Read → 灵活但无事务/无治理
湖仓一体:  数据湖存储(对象存储) + 表格式(Iceberg/Hudi/Delta) + OLAP引擎 → 灵活+事务+高性能
```

**Iceberg核心设计**(架构师重点理解)：
```
Snapshot: 每次写入产生新Snapshot → 指向Manifest List → 指向Manifest File → 指向Data File
Snapshot隔离: 读旧Snapshot → 不受新写入影响 → 实现MVCC
Schema Evolution: 加列/删列/改类型 → 无需重写数据 → 只改Metadata
分区演进:   改分区策略 → 无需重写数据 → 只改Metadata
时间旅行:   SELECT * FROM t FOR SYSTEM_TIME AS OF timestamp → 读历史Snapshot

与Flink/Spark集成:
  Flink写入Iceberg → Flink读Iceberg → 实时+批处理统一存储层
```

## S13 领域驱动设计与架构方法论

> 架构师视角：DDD不是编码技巧，而是业务建模方法论。它是从"技术架构师"到"业务架构师"的桥梁——技术架构师知道怎么用技术，业务架构师知道业务该怎么拆。

### 13.1 DDD战略设计

**限界上下文(Bounded Context)**——微服务拆分的依据：
```
电商系统限界上下文划分:
  商品上下文:   商品/分类/品牌/SKU/库存(读多写少)
  订单上下文:   订单/订单项/物流(写多,核心域)
  支付上下文:   支付/退款/账务(强一致,核心域)
  用户上下文:   用户/地址/认证(支撑域)
  营销上下文:   优惠券/活动/积分(支撑域)
  搜索上下文:   索引/推荐(通用域)

每个限界上下文 = 一个微服务 = 一个独立部署单元 = 一个团队
```

**上下文映射(Context Map)**——限界上下文之间的关系：
```
合作(Cooperation):     两个团队协同开发(最紧密)
客户-供应(UD):         下游依赖上游,上游需考虑下游需求
防腐层(ACL):           下游用ACL翻译上游数据格式 → 隔离上游变化
开放主机服务(OHS):     上游提供标准协议(REST/gRPC) → 减少集成成本
发布语言(PL):          上下文间用事件/DTO通信 → 异步解耦

防腐层是架构师最该用的模式:
  订单服务调用支付服务 → 不直接用支付服务的DTO → 而是定义自己的PaymentClient接口
  → 支付服务变更 → 只改ACL的适配逻辑 → 订单服务代码不动
```

### 13.2 DDD战术设计

**聚合(Aggregate)**——一致性边界：
```
聚合根:     聚合的入口对象,外部只能通过聚合根访问聚合内对象
实体:       有唯一标识,可变(如Order有orderId)
值对象:     无唯一标识,不可变(如Money/Address),比较按值而非引用

聚合设计原则:
  1. 聚合要小(只包含强一致性要求的对象)
  2. 聚合间通过ID引用(而非直接引用对象)
  3. 一个事务只修改一个聚合(跨聚合用领域事件→最终一致)
  
例: Order聚合包含OrderItem(强一致,订单项必须在订单内)
   但Order不包含User(弱一致,通过userId引用)
```

**领域事件(Domain Event)**——跨聚合/跨上下文通信：
```
发布-订阅模式:
  聚合A修改 → 发布OrderCreatedEvent → MQ → 聚合B/上下文C订阅处理

事件设计:
  命名: 过去时态(OrderCreated / PaymentSucceeded / InventoryReserved)
  内容: 包含事件发生时的必要数据(不依赖发布者后续状态)
  不可变: 事件一旦发布不可修改

与微服务的关系:
  领域事件 → 转为Integration Event → 发到MQ → 其他服务订阅
  → 这是微服务间异步通信的最佳实践(解耦+可靠+可审计)
```

### 13.3 CQRS与事件溯源

**CQRS架构**：
```
命令侧(写):
  Controller → Command → CommandHandler → DomainModel(聚合) → Event → WriteDB(MySQL)
  
查询侧(读):
  Event → EventHandler → ReadModel(投影) → ReadDB(ES/Redis/ClickHouse)
  
优势:
  - 写侧用关系型DB保证一致性,读侧用专用引擎优化查询
  - 读写模型独立演化(写侧加字段不影响读侧查询)
  - 适合写少读多/读写模型差异大/查询维度多的场景

代价:
  - 架构复杂度增加(两套模型+事件同步)
  - 数据最终一致(读侧可能有延迟)
  - 不适合CRUD为主的简单业务
```

### 13.4 架构风格

**六边形架构(端口与适配器)**：
```
核心(领域层):     领域模型+领域服务+领域事件 → 不依赖任何框架
端口(接口):       入站端口(用例接口) + 出站端口(仓储/通知接口)
适配器(实现):     入站适配器(RestController/gRPC) + 出站适配器(MySQLRepo/RedisRepo/KafkaProducer)

依赖规则: 适配器依赖端口 → 端口定义在核心 → 核心不依赖适配器
意义: Spring/MyBatis等技术细节被推到外层 → 替换技术框架不影响领域模型
```

**架构决策记录(ADR)**——架构师必须养成的习惯：
```markdown
# ADR-001: 选择RocketMQ而非Kafka作为业务消息队列

## 状态: 已采纳

## 上下文
系统需要事务消息和延迟消息能力，团队Java为主，QPS预估5万

## 决策
选择RocketMQ，理由：
1. 原生支持事务消息(Kafka不支持跨系统事务)
2. 原生支持延迟消息(Kafka需自行实现)
3. Java生态，团队学习成本低
4. 阿里开源，国内社区活跃

## 后果
- 正面: 满足业务需求，团队上手快
- 负面: 大数据集成不如Kafka(Flink Kafka Connector更成熟)
- 缓解: 数据管道场景单独引入Kafka
```

## S14 设计模式与架构风格

### 14.1 七种必须精通的GoF模式

**策略模式**(运行时算法切换)：
```java
// 支付策略: 微信/支付宝/银行卡 → 运行时根据用户选择切换
interface PaymentStrategy {
    PayResult pay(Order order);
}
class WechatPayStrategy implements PaymentStrategy { ... }
class AlipayPayStrategy implements PaymentStrategy { ... }

// Spring中: 用Map<String, Strategy>自动注入所有实现
@Component
class PaymentStrategyFactory {
    @Autowired Map<String, PaymentStrategy> strategyMap;
    public PaymentStrategy get(String type) { return strategyMap.get(type); }
}
```

**模板方法模式**(定义算法骨架)：
```java
// Spring AbstractApplicationContext.refresh() = 最经典的模板方法
// 定义了12个步骤,子类可重写部分步骤(onRefresh/validate等)
abstract class AbstractClass {
    public final void templateMethod() {  // final防止子类重写骨架
        step1();
        step2();  // 子类可重写
        step3();
    }
    protected abstract void step2();
}
```

**责任链模式**(请求沿链传递)：
```java
// Servlet Filter Chain / Spring Interceptor Chain / Sentinel Slot Chain
// 每个节点决定: 处理并传递 / 处理并终止 / 不处理传递
interface Handler {
    boolean handle(Request request, Chain chain);
}
```

### 14.2 并发设计模式

**Copy-on-Write模式**：
```
读多写极少场景: CopyOnWriteArrayList / CopyOnWriteArraySet
原理: 写时复制整个底层数组 → 新数组上修改 → 替换引用 → 读不加锁
代价: 写时内存翻倍 + 弱一致性(迭代器遍历的是快照)
适用: 事件监听器列表/配置列表/白名单(写极少读多)
```

**Two-Phase Termination模式**(优雅关闭)：
```java
// 线程池shutdown()就是这个模式
// 阶段1: 设置关闭标志(shutdown=true) → 拒绝新任务
// 阶段2: 等待已提交任务完成(awaitTermination) → 超时后强制中断(shutdownNow)
```

### 14.3 架构级模式

**微内核架构**(Eclipse/VSCode/IDEA)：
```
Core(微内核): 插件加载器+扩展点注册+事件总线
Plugins:     每个插件实现扩展点接口 → 独立开发/部署/升级

Java实现:   java.util.ServiceLoader(SPI机制)
            → META-INF/services/接口全限定名 → 实现类全限定名
            
Spring实现: @Conditional + spring.factories → 自动装配本质也是插件化
```

## S15 AI工程化深化

> 架构师视角：AI工程化不是"跑通Demo"，而是"能上生产"——降低幻觉+控制成本+保证安全+可观测。你已有Spring AI基础，这个阶段要补生产化。

### 15.1 RAG架构深化

**四代RAG演进**：
```
L1 朴素RAG:
  query → Embedding → 向量检索TopK → 拼Prompt → LLM生成
  问题: 召回率低/幻觉/上下文窗口浪费

L2 查询改写+重排序:
  query → LLM改写/扩展/分解 → 多路检索(向量+BM25) → RRF融合 → Reranker重排 → LLM
  改进: 召回率↑/精度↑/减少无关文档

L3 Self-RAG/Corrective-RAG:
  检索后: LLM自评估文档相关性 → 不相关则重新检索/改写
  生成后: LLM自评估答案事实性 → 不准确则重新检索+生成
  改进: 自适应检索+自我纠正

L4 高级RAG:
  查询路由: 不同类型问题走不同检索路径(事实类→向量,代码类→关键词,表格类→SQL)
  自查询: LLM把自然语言转结构化查询(Milvus filter条件)
  上下文压缩: 长文档→LLM摘要/提取关键句→减少Token消耗
  流式生成: SSE流式输出→用户体验↑
```

**Chunking策略**(架构师必须关注)：
```
固定长度(500-1000字): 简单但可能截断语义
语义切片: 按段落/章节/句子边界切 → 语义完整但长度不均
递归切片: 先按大单位(章节)→再按小单位(段落)→直到长度达标
文档结构切片: 按Markdown标题/代码块/表格切 → 保留结构信息
```

### 15.2 Agent架构深化

**三种Agent模式**：
```
ReAct(Reasoning+Acting): 
  思考→行动→观察→思考→行动→...→回答
  例: "上海今天天气?" → 思考"需要查天气" → 调用weather_tool("上海") → 观察结果 → 回答

Plan-and-Execute:
  先规划完整步骤 → 再逐步执行 → 适合复杂任务
  例: "写一篇技术报告" → 规划[调研/写大纲/写正文/审校] → 逐步执行

Reflexion:
  执行→自我评估→反思不足→重新执行 → 适合需要迭代改进的任务
  例: "写代码" → 写初版 → 自评估"有Bug" → 反思"边界条件没处理" → 重写
```

**MCP协议(Model Context Protocol)**：
```
Anthropic提出的标准化协议 → 让LLM统一地与外部工具/资源交互

MCP架构:
  MCP Host(LLM应用,如Claude Desktop/IDE插件)
    → MCP Client(协议客户端)
      → MCP Server(工具提供者,如文件系统/数据库/Git/浏览器)

三种原语:
  Tools:    LLM可调用的函数(如query_database, search_web)
  Resources: LLM可读取的数据(如文件内容, 数据库schema)
  Prompts:   预定义的Prompt模板(如"分析这个代码")

架构师意义: 一次实现MCP Server → 所有支持MCP的LLM客户端都能用 → 避免重复开发
```

### 15.3 AI可观测与治理

**Token计量与成本控制**：
```
模型成本差异(2026年参考):
  GPT-4o:    输入$2.5/1M tokens, 输出$10/1M tokens
  Claude 3.5: 输入$3/1M tokens, 输出$15/1M tokens
  Qwen-Max:  输入¥2/1M tokens, 输出¥6/1M tokens
  DeepSeek:  输入¥1/1M tokens, 输出¥2/1M tokens

成本控制策略:
  1. 模型路由: 简单问题→小模型(便宜), 复杂问题→大模型(贵)
  2. 缓存: 相同Prompt→缓存结果→避免重复调用
  3. Token预算: 每用户/每接口设置Token上限→超额降级
  4. Prompt精简: 减少System Prompt长度→省输入Token
```

**幻觉检测与缓解**：
```
事实性校验:   生成答案 → 检索权威来源 → 比对一致性 → 不一致则标记
引用验证:     要求LLM每个声明附带引用来源 → 人工/自动验证来源可靠性
置信度评估:   生成答案+置信度 → 低置信度→人工审核流程
RAGAS评估:    忠诚度(faithfulness)/答案相关性/上下文相关性 → 量化RAG质量
```

## S16 业务架构与技术战略

> 架构师视角：这是架构师路线的终极形态。技术深度让你成为高级开发，业务理解+技术判断力让你成为架构师，组织影响力让你成为技术总监。

### 16.1 业务建模

**三域识别**(资源分配的依据)：
```
核心域(Core Domain):   企业核心竞争力,必须自研,投入最多资源
  例: 电商的订单/支付/推荐; 支付的账户/清算; 社交的推荐/内容

支撑域(Supporting Domain): 必要但非核心,可选自研或采购
  例: 用户认证/通知/权限/日志/监控

通用域(Generic Domain):   通用能力,优先采购SaaS/开源
  例: OA/HR/邮件/IM/报表/文件存储

架构师资源分配:
  核心域: 投入80%精力 → 自研+深耕+持续优化
  支撑域: 投入15%精力 → 选型+适度定制
  通用域: 投入5%精力 → 采购+集成
```

### 16.2 中台架构与反思

**中台价值**：
```
业务中台: 用户中心/商品中心/订单中心 → 能力复用 → 避免每个应用重复建设
数据中台: 指标体系/数据资产/数据服务化 → 数据能力开放 → 赋能业务决策
技术中台: MQ/缓存/网关/监控/配置中心 → 基础设施标准化 → 降低业务开发门槛
```

**中台反思**(阿里从"大中台"到"多元化"的演进)：
```
过度中台的代价:
  1. 抽象泄露: 通用模型无法满足所有业务 → 业务方被迫适配 → 开发效率反而下降
  2. 沟通成本: 业务方+中台方对齐需求 → 协作成本>独立开发
  3. 创新抑制: 统一模型限制业务差异化 → "为了中台而中台"
  4. 维护负担: 中台承载所有业务需求 → 越来越臃肿 → 改一个功能影响所有业务

正确姿势:
  - 不是所有能力都需要中台化 → 按业务成熟度判断
  - 中台不是一成不变 → 随业务演进拆分(从统一中台→领域中台)
  - 康威定律: 中台团队结构要匹配业务边界
  - 阿里2020年后: 从"大中台小前台" → "多元化中台" → 按业务域拆分中台
```

### 16.3 技术雷达与演进式架构

**技术雷达四环**：
```
Adopt(采用):   经过验证,推荐全团队使用
  例: Spring Boot 3 / Java 17 / Redis Cluster / Prometheus

Trial(试验):   在小范围试点,积累经验
  例: ZGC / K8s Service Mesh / Spring AI / Flink

Assess(评估):   值得关注和研究,但暂不使用
  例: GraalVM Native Image / HTTP/3 / Serverless

Hold(暂缓):    不推荐使用(有更好的替代/有已知问题)
  例: JDK8 CMS(用G1/ZGC替代) / Eureka(用Nacos替代) / 单体架构
```

**演进式架构(Evolutionary Architecture)**：
```
核心理念: 架构不是一次设计到位,而是持续演进 → 每次变更都应该让架构变得更好

适应度函数(Fitness Function):
  → 一组自动化约束,保护架构的重要特性
  例: 架构测试(依赖方向正确) / 性能基线(P99<200ms) / 安全扫描(无高危漏洞)
  
实现: ArchUnit(Java架构测试框架)
  @ArchTest
  static final ArchRule layer_dependencies = 
      layeredArchitecture()
          .consideringAllDependencies()
          .layer("Controller").definedBy("..controller..")
          .layer("Service").definedBy("..service..")
          .layer("Domain").definedBy("..domain..")
          .layer("Infrastructure").definedBy("..infrastructure..")
          .whereLayer("Controller").mayOnlyAccessLayers("Service")
          .whereLayer("Service").mayOnlyAccessLayers("Domain", "Infrastructure")
          .whereLayer("Domain").mayOnlyAccessLayers();  // 领域层不依赖任何外层
```

### 16.4 康威定律与团队拓扑

**康威定律**：系统架构反映组织架构——4个团队开发的系统会有4个模块。

**逆康威定律**：先设计期望的架构 → 再调整组织结构来匹配。

**团队拓扑四种类型**：
```
流对齐团队(Stream-Aligned):    端到端负责一个业务流(如订单团队,包含前端+后端+测试)
使能团队(Enabling):            为流对齐团队提供能力(如架构组/工具组/安全组)
复杂子系统团队(Complicated Subsystem): 负责高复杂度子系统(如推荐算法/支付引擎)
平台团队(Platform):            提供自服务平台(如K8s平台/监控平台/CI/CD平台)

团队认知负载原则:
  - 每个团队的认知负载有限 → 不要让一个团队负责太多不同领域
  - 流对齐团队2-8人(2-pizza rule)
  - 平台团队提供"足够薄"的平台API → 降低流对齐团队的认知负载
```

### 16.5 架构师软技能

**技术方案评审Checklist**(架构师必备)：
```
□ 业务价值: 解决什么业务问题? 量化指标是什么?
□ 方案对比: 至少2种备选方案,各优劣和适用场景
□ 技术选型: 为什么选A不选B? 性能/可靠性/生态/团队熟悉度?
□ 容量评估: 预估QPS/数据量/存储量 → 需要多少资源?
□ 高可用设计: 限流/熔断/降级预案? 单点故障? 数据一致性?
□ 可观测性: 监控指标/告警规则/日志规范/链路追踪?
□ 安全审计: 认证/授权/数据加密/敏感信息脱敏?
□ 扩展性: 预计未来变化? 是否支持水平扩展? Schema演进?
□ 成本评估: 机器成本+运维成本+人员成本 → TCO(总拥有成本)
□ 迁移方案: 有旧系统? 如何平滑迁移? 回滚方案?
□ 里程碑: 分几个阶段交付? 每阶段验收标准?
```

**架构师成长路径**：
```
初级架构师(P7/T6):  能做技术选型+系统设计+解决技术难题 → 技术深度是基础
中级架构师(P8/T7):  能做跨团队架构设计+技术规划+推动落地 → 业务理解+影响力
高级架构师(P9/T8):  能做技术战略+组织赋能+技术文化建设 → 判断力+领导力
技术总监(VP):       能做技术路线图+团队建设+业务技术对齐 → 战略思维+组织能力

核心跃迁:
  技术深度 → 技术广度 → 业务理解 → 技术判断力 → 组织影响力
  你现在在第一阶段,速览版路线帮你快速建立广度
  实习和工作帮你建立业务理解和判断力
  影响力需要时间积累,但可以从写技术博客/内部分享/带新人开始
```
